# 시나리오 02: 공통컴포넌트 탐색과 활용

## 목적

표준프레임워크 공통컴포넌트 자산을 폐쇄망에서 본 MCP를 통해 **검색 → 상세 조회 → 의존성 확인 → 소스/DDL/DML 조회**의 흐름으로 활용할 수 있는지 확인합니다. 긴 소스 파일과 초기 데이터를 구간으로 나눠 조회할 수 있는지, 입력이 잘못되었을 때 도구가 돌려주는 안내를 LLM이 활용하는지도 함께 확인합니다.

## 검증 도구

- `egov_search_knowledge` (`scope`: `components`)

## 사전조건

- 시나리오 00 통과
- 설치 경로에 `knowledge-base/egovframe.db`(공통컴포넌트 메타데이터)와 `templates/common-components-src/`(공통컴포넌트 소스)가 있음

## 시나리오

### 2-1) 공통컴포넌트 검색

```text
게시판 기능을 구현할 때 참고할 만한 표준프레임워크 공통컴포넌트를 찾아줘. 컴포넌트 ID와 패키지명도 알려줘.
```

**기대 호출**

```json
{ "scope": "components", "query": "게시판" }
```

**기대 결과**

- `## 공통컴포넌트 목록 (13개)` 아래에 컴포넌트 ID, 컴포넌트, 카테고리, 패키지명, 버전 열의 표가 나옴
- 표에 `bbs`(게시판), `tpl`(게시판 템플릿), `cmt`(댓글관리), `scp`(스크랩기능), `stf`(만족도조사)가 들어 있음
- 공통컴포넌트의 `query`는 의미 검색이 아니라 키워드 검색에 쓰임. 검색어가 컴포넌트 ID, 이름, 영문명, 설명, 영문 설명, 패키지명 가운데 하나에 부분 문자열로 들어 있으면 일치하고, 모든 검색어가 일치하는 컴포넌트를 먼저 찾음
- `게시판 기능 구현`처럼 모든 검색어가 들어 있는 컴포넌트가 없는 `query`는 일부 검색어가 들어 있는 컴포넌트로 대체되고, 제목 아래에 `> 모든 검색어가 들어 있는 항목이 없어, 검색어 2개 가운데 1개 이상이 들어 있는 항목을 표시합니다 (검색어: 게시판, 기능).`과 `> 일치하는 항목이 없어 검색에 쓰지 않은 낱말: 구현.`이 붙음
- `게시판 컴포넌트`처럼 모든 컴포넌트에 해당하는 낱말(`컴포넌트`, `공통컴포넌트`, `표준프레임워크` 등)을 함께 적은 `query`는 그 낱말을 빼고 찾아서 같은 13개를 돌려주고, `> 한 글자이거나, 영어 기능어이거나, 목록의 모든 항목에 해당해 검색에 쓰지 않은 낱말: 컴포넌트.`가 붙음
- 낱말을 단독 `OR`로 이은 `query`는 그 가운데 하나라도 들어 있는 컴포넌트를 모두 돌려줌. `게시판 댓글`은 두 낱말이 모두 들어 있는 `cmt`(댓글관리) 1개만 돌려주지만, `게시판 OR 댓글`은 13개를 돌려주고 제목 아래에 `> query 에 OR 가 있어, 검색어 2개 가운데 1개 이상이 들어 있는 항목을 표시합니다 (검색어: 게시판, 댓글).`이 붙음
- `query` 대신 `filters.keyword: "게시판"`을 준 호출도 유효함. 이때는 카테고리별로 묶인 표에 설명 열이 나옴

### 2-2) 컴포넌트 상세 조회

```text
bbs 공통컴포넌트의 구조와 의존성, 사용 테이블을 정리해서 보여줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "get", "filters": { "componentId": "bbs" } }
```

```json
{ "scope": "components", "action": "dependencies", "filters": { "componentIds": ["bbs"] } }
```

**기대 결과**

- 첫 번째 호출은 `## 게시판` 아래에 기본 정보(ID `bbs`, 패키지명 `egovframework.com.cop.bbs`), 설명, 사용 테이블, 의존성(직접 의존하는 패키지 14개와 컴포넌트명의 표)을 돌려줌
- 두 번째 호출은 `## 의존성 해결 결과` 아래에 요청한 컴포넌트, 자동 추가된 의존성(20개), 전체 필요 컴포넌트(21개), 필요 패키지 목록을 돌려줌. 컴포넌트 목록에 없는 의존 패키지(`egovframework.com.cop.clb`)는 `컴포넌트 정보가 없는 의존 패키지`로 따로 나옴
- `action: "get"`을 생략하고 `filters.componentId`만 줘도 상세 정보가 나오며, `dependencies`는 `componentIds` 배열 대신 `componentId` 하나를 줘도 됨

### 2-3) 소스 파일 목록과 단일 파일 조회

```text
bbs 공통컴포넌트에 어떤 Java/Mapper XML/JSP 파일이 있는지 목록을 보여주고, 그 중 게시글 컨트롤러 파일을 열어서 어떤 메서드가 있는지 요약해줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "sourceFiles", "filters": { "componentId": "bbs" } }
```

```json
{ "scope": "components", "action": "readSource", "filters": { "filePath": "src/main/java/egovframework/com/cop/bbs/web/EgovArticleController.java" } }
```

```json
{ "scope": "components", "action": "readSource", "filters": { "filePath": "src/main/java/egovframework/com/cop/bbs/web/EgovArticleController.java", "offset": 30000 } }
```

**기대 결과**

- 첫 번째 호출은 `## 게시판 소스 파일 목록` 아래에 Java 소스, MyBatis Mapper XML, JSP 뷰 같은 종류별 경로 목록(총 88개)을 돌려주고, 끝에 `readSource` 호출 방법과 목록의 수집 범위를 안내함. 목록에는 패키지 경로(`com/cop/bbs`)와 같은 디렉토리에 있는 파일과 이 컴포넌트에 귀속되는 Spring 설정만 실림
- 두 번째 호출은 `filters.filePath`에 목록의 경로를 그대로 넣으며, 머리말 ``**파일**: `src/main/java/egovframework/com/cop/bbs/web/EgovArticleController.java` (50,362 bytes, java)``와 코드 블록을 돌려줌. `readSource`는 한 번에 30,000자까지 돌려주므로 끝에 ``> 전체 47,640자 중 1~30,000자를 표시했습니다. 이어서 읽으려면 같은 호출에 `filters.offset: 30000` 을 주세요.``가 붙음
- 세 번째 호출은 나머지를 돌려주고, 끝에 `> 전체 47,640자 중 30,001~47,640자를 표시했습니다 (파일의 끝).`이 붙음
- LLM이 `filters.componentId`를 함께 보내도 파일은 그대로 읽히고, 끝에 `> 이 조회에 적용되지 않아 무시한 필터: componentId.`가 붙음
- LLM이 파일 본문을 근거로 메서드를 요약함. 요약에 30,000자 뒤에만 나오는 메서드(`deleteGuestList`, `selectBlogMasterList`, `previewBlogMainPage` 등)가 들어 있으면 파일을 끝까지 읽은 것임

### 2-4) DDL / DML 조회

```text
bbs 공통컴포넌트가 필요로 하는 MySQL 테이블 생성 DDL과 초기 데이터 DML을 추출해줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "ddl", "filters": { "componentId": "bbs", "dbType": "mysql" } }
```

```json
{ "scope": "components", "action": "dml", "filters": { "componentId": "bbs", "dbType": "mysql" } }
```

**기대 결과**

- 첫 번째 호출은 `## 게시판 DDL (mysql)` 아래에 `- **필요 테이블**: 31개`, `- **추출된 DDL**: 30개 테이블, 1개 뷰`와 함께 `CREATE TABLE`, `CREATE UNIQUE INDEX`, `CREATE INDEX`, `CREATE VIEW` 문을 돌려줌
- 두 번째 호출은 `## 게시판 초기 데이터 (mysql)` 아래에 `INSERT INTO` 문을 돌려줌. 기본 보기는 테이블마다 처음 20건만 싣기 때문에 `전체 654건 중 107건 표시 (테이블마다 처음 20건)`로 나오고, 테이블별 전체·표시·생략 건수의 표와 한 테이블을 나눠 조회하는 방법의 안내가 함께 나옴

### 2-5) 초기 데이터 구간 조회

2-4에 이어서 다음을 입력합니다.

```text
COMTCCMMNCODE 테이블의 초기 데이터를 50건씩 나눠서 끝까지 보여줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "dml", "filters": { "componentId": "bbs", "dbType": "mysql", "table": "COMTCCMMNCODE" }, "limit": 50 }
```

```json
{ "scope": "components", "action": "dml", "filters": { "componentId": "bbs", "dbType": "mysql", "table": "COMTCCMMNCODE", "offset": 50 }, "limit": 50 }
```

**기대 결과**

- 첫 번째 호출은 `총 76건 중 1~50`을 돌려주고, 끝에 ``> 남은 26건은 같은 호출에 `filters.offset: 50` 을 주어 이어서 조회할 수 있습니다.``가 붙음
- 두 번째 호출은 `총 76건 중 51~76`을 돌려주고 안내가 붙지 않음
- `limit`을 생략하면 한 번에 100건(최댓값)까지 돌려줌. 100을 넘는 값을 주면 100으로 줄여 적용하고 `> 요청한 limit 150 은(는) dml 구간 조회의 최댓값 100 으로 줄여 적용했습니다.`를 붙임
- 컴포넌트가 쓰지 않는 테이블 이름을 주면 쓸 수 있는 테이블 이름을 나열한 `isError` 응답이 돌아옴

### 2-6) 없는 컴포넌트 ID의 후보 안내

```text
blog 공통컴포넌트의 상세 정보를 보여줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "get", "filters": { "componentId": "blog" } }
```

**기대 결과**

- `컴포넌트를 찾을 수 없습니다: blog`와 함께 비슷한 컴포넌트로 `blog-management` 블로그관리(`egovframework.com.cop.bbs`)가 안내됨
- LLM이 안내된 ID로 다시 호출함(`filters.componentId: "blog-management"`). 이 호출은 `## 블로그관리`의 상세 정보를 돌려줌

### 2-7) 지원하지 않는 DB와 쓰이지 않은 입력의 안내

```text
bbs 공통컴포넌트의 H2용 테이블 생성 DDL을 보여줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "ddl", "filters": { "componentId": "bbs", "dbType": "h2" } }
```

**기대 결과**

- `isError` 응답으로 `지원하지 않는 DB 타입입니다: h2 (지원: mysql, maria, oracle, postgres, tibero, cubrid, altibase, goldilocks. 별칭: mariadb, postgresql, pgsql)`가 돌아옴
- LLM이 H2는 지원하지 않는다고 답하고 지원하는 DB를 알려 줌

이어서 다음을 입력합니다.

```text
bbs 공통컴포넌트의 상세 정보를 Oracle 기준으로 보여줘.
```

**기대 호출**

```json
{ "scope": "components", "action": "get", "filters": { "componentId": "bbs", "dbType": "oracle" } }
```

**기대 결과**

- `## 게시판`의 상세 정보가 나오고, 끝에 `> 이 조회에 적용되지 않아 무시한 필터: dbType. (dbType 은(는) action "ddl" 또는 "dml" 에서 씁니다.)`가 붙음
- 선택된 조회가 쓰지 않는 필터는 오류 없이 무시되고 이렇게 그 키가 안내됨. 상세 정보는 DB 종류에 따라 달라지지 않으며 `dbType`은 `ddl`과 `dml`에서만 쓰임
- `action`을 준 조회는 `query`를 쓰지 않고, `limit`은 `dml`에 `filters.table`을 준 구간 조회에서만 씀. 쓰이지 않는 `query`나 `limit`을 함께 보내면 끝에 `> 이 조회에 쓰이지 않아 무시한 파라미터: query, limit.`처럼 그 이름이 안내됨
- `action` 없이 `action` 전용 필터만 준 호출(예: `{ "scope": "components", "filters": { "dbType": "oracle" } }`)은 목록으로 답하지 않고, `isError` 응답으로 `action 을 지정하지 않아 다음 필터를 쓸 수 없습니다: filters.dbType 은(는) action "ddl" 또는 "dml" 와(과) 함께 씁니다.`를 돌려줌
- LLM이 이 안내를 답에 반영하는지, 또는 `action: "ddl"`로 Oracle용 DDL을 이어서 조회하는지 확인함

## 합격 기준

- [ ] 2-1에서 `bbs`를 포함한 게시판 관련 공통컴포넌트가 반환된다.
- [ ] 2-2에서 컴포넌트 상세 정보와 의존성 해결 결과가 모두 응답에 포함된다.
- [ ] 2-3에서 LLM이 소스 파일 본문을 끝까지 읽은 뒤 메서드를 요약한다(추측이 아닌 인용).
- [ ] 2-4에서 `CREATE TABLE`과 `INSERT INTO` SQL이 반환된다.
- [ ] 2-5에서 두 번의 호출로 76건이 빠짐없이 조회된다.
- [ ] 2-6에서 LLM이 안내된 `blog-management`로 다시 조회한다.
- [ ] 2-7에서 LLM이 H2는 지원하지 않는다고 답하고, `dbType`이 무시되었다는 안내를 답에 반영한다.

## 점검 포인트

- 공통컴포넌트 ID를 모를 때는 키워드 검색을 먼저, ID를 알 때는 `action: "get"`을 바로 사용하도록 LLM이 분기하는지 봅니다. `filters.componentId`에는 컴포넌트 ID 외에 패키지명(예: `egovframework.com.cop.tpl`)이나 정확한 컴포넌트 이름(예: `게시판`)도 쓸 수 있습니다.
- `bbs`는 게시판입니다. 같은 패키지(`egovframework.com.cop.bbs`)를 쓰는 블로그관리의 ID는 `blog-management`입니다.
- `scope`를 생략해도 `action`이나 `filters.componentId`가 있으면 공통컴포넌트 조회로 처리됩니다. 반대로 `scope` 없이 `query: "게시판"`만 보내면 통합 검색이 실행되어 공통컴포넌트는 5건까지만 나옵니다.
- `filters.categoryId`에는 카테고리 ID, 한글 이름, 영문 이름 가운데 하나를 넣습니다(예: `게시판`, `BBS`). 어느 카테고리도 아닌 값을 주면 0건이 되고, 카테고리 ID 37개를 나열한 안내가 붙습니다.
- `dbType`을 `oracle`, `postgres` 등으로 바꿨을 때도 2-4와 같은 흐름이 동작하는지 추가로 검증할 수 있습니다. 지원하는 값은 `mysql`(기본), `maria`, `oracle`, `postgres`, `tibero`, `cubrid`, `altibase`, `goldilocks`입니다. `cubrid`의 스크립트는 외래 키를 `ALTER` 문으로 따로 두기 때문에, `bbs`의 `cubrid` DDL에는 머리말에 `- **외래 키 제약**: 17건 (ALTER 문, DDL 끝에 실음)`이 더 나오고, 그 문들이 초기 데이터를 넣은 뒤에 실행하라는 주석과 함께 DDL 끝에 실립니다.
- 외래 키가 참조하는 테이블이 컴포넌트의 사용 테이블에 없으면 그 테이블의 DDL도 함께 실리고, 머리말에 따로 적힙니다. 예를 들어 `qqm`(질문관리)의 MySQL DDL에는 `- **외래 키 참조로 함께 실은 테이블**: 1개 (COMTNQUSTNRTMPLAT)`가 나옵니다.
- 응답 크기에 유의합니다. 2-4의 DDL은 약 2만 1천 자, DML 기본 보기는 약 2만 3천 자이고, 2-3의 `EgovArticleController.java`는 두 번의 호출을 합쳐 약 4만 8천 자입니다. 컨텍스트가 작은 모델에서는 2-3의 대상을 한 번에 읽히는 `EgovBBSMasterController.java`(약 1만 7천 자)로 바꿔 수행합니다.
- `readSource`가 한 번에 돌려주는 분량은 30,000자입니다. 더 긴 파일은 응답 끝에 안내된 `filters.offset`을 더해 이어서 읽습니다. 예를 들어 107,493자인 `src/main/webapp/js/egovframework/com/cmm/EgovValidation.js`는 `filters.offset`을 30000, 60000, 90000으로 늘려 네 번에 나눠 읽습니다.
