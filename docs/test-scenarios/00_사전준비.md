# 시나리오 00: 사전 준비와 설치 검증

## 목적

폐쇄망에 반입한 본 MCP가 OSS LLM 클라이언트에서 정상적으로 인식되고, `egov_search_knowledge` 도구 1개가 노출되는지 확인합니다. 이 시나리오가 실패하면 이후 모든 시나리오를 진행할 수 없습니다.

## 사전조건

- 폐쇄망 서버에 Node.js 22 설치(`node -v`의 결과가 `v22.x`)
- 인터넷이 되는 Node.js 22 환경에서 `npm run pack:platforms`로 만든 배포 tgz 가운데 서버의 OS와 CPU에 맞는 파일(`dist/egovframe-mcp-search-<버전>-<os>-<cpu>.tgz`, 예: `egovframe-mcp-search-1.0.0-linux-x64.tgz`)을 폐쇄망으로 반입

배포 tgz에는 `build/`, `node_modules/`(네이티브 바이너리 포함), `knowledge-base/`(구축된 인덱스), `models/`(임베딩 모델), `templates/common-components-src/`(공통컴포넌트 소스), `docs/`(이 시나리오를 포함한 문서)가 들어 있습니다. 그래서 폐쇄망에서는 사내 npm 미러가 필요 없고, 설치한 뒤에 `npm install`, `npm run build`, `npm run build-index`를 실행하지 않습니다. 동봉된 `better-sqlite3` 바이너리는 tgz를 만든 Node.js 22와 대상 플랫폼에 고정되어 있으므로, 서버를 실행하는 Node.js도 22여야 합니다.

이 시나리오는 tgz를 설치 경로에 직접 푸는 방법으로 설치합니다. [저장소 README](../../README.md)의 안내대로 tgz를 `npm install -g`로 전역 설치한 환경에서는, 아래의 설치 경로를 `npm root -g`가 출력한 디렉토리 아래의 `egovframe-mcp-search`로 바꿔 읽습니다. 저장소를 클론한 개발 환경에서 시나리오를 수행할 때는 저장소 README의 설치 절차를 따르고, 아래의 설치 경로를 클론한 디렉토리로 바꿔 읽습니다.

## 절차

### 1) 설치와 설치 상태 확인

반입한 tgz를 설치 경로(예: `/opt/egovframe-mcp-search`)에 풉니다.

```bash
node -v    # v22.x
mkdir -p /opt/egovframe-mcp-search
tar -xzf egovframe-mcp-search-1.0.0-linux-x64.tgz -C /opt/egovframe-mcp-search --strip-components=1
node /opt/egovframe-mcp-search/build/index.js --version    # 패키지 버전(예: 1.0.0)
```

설치 경로에 다음이 있어야 합니다.

- `build/index.js`
- `node_modules/`
- `knowledge-base/egovframe.db`
- `knowledge-base/egovframe_guide.lance/`
- `knowledge-base/developer_knowledge.lance/`
- `models/Xenova/multilingual-e5-small/`
- `templates/common-components-src/pom.xml`

> 설치 경로에서 `npm install`이나 `npm run build`를 실행하지 않습니다. `build` 스크립트는 `build/`를 먼저 지운 뒤 TypeScript를 컴파일하는데, 배포 tgz에는 `src/`와 컴파일러가 없어서 `build/index.js`가 사라진 채로 끝납니다. `npm install`도 `prepare` 스크립트로 같은 빌드를 실행합니다.

### 2) MCP 클라이언트 등록

폐쇄망에서 사용하는 OSS LLM 클라이언트의 MCP 설정 파일에 다음과 같이 등록합니다.

```json
{
  "mcpServers": {
    "egovframe-mcp-search": {
      "command": "node",
      "args": ["/opt/egovframe-mcp-search/build/index.js"]
    }
  }
}
```

서버는 `build/index.js`가 있는 설치 경로에서 `knowledge-base/`, `models/`, `templates/common-components-src/`를 스스로 찾으므로, 경로를 알려 주는 환경 변수는 필요 없습니다. `command`의 `node`가 Node.js 22가 아니면 Node.js 22 실행 파일의 절대 경로를 적습니다.

### 3) 도구 목록 확인

LLM 클라이언트에서 본 MCP 서버를 활성화한 뒤, **`egov_search_knowledge` 1개가 노출되는지** 확인합니다.

| # | 도구 | 분류 |
|---|------|------|
| 1 | `egov_search_knowledge` | 통합 지식 검색(읽기 전용) |

서버는 연결할 때 초기화 응답의 `instructions`로 사용법 요약도 함께 보냅니다. 내용은 출처를 `scope`로 고르고, `action`은 `components`에서만 쓰며, 필터는 모두 `filters` 객체 안에 넣는다는 것입니다.

MCP Inspector의 `Tools` 탭에서 목록과 입력 스키마를 직접 확인할 수도 있습니다. 다만 `npm run inspector`는 `npx`로 `@modelcontextprotocol/inspector` 패키지를 내려받아 실행하므로, 폐쇄망에서는 이 패키지를 받을 수 있는 사내 npm 미러가 있을 때만 쓸 수 있습니다.

> 위 도구 외에 다른 도구가 보이면 예전 빌드로 만든 배포본입니다. 이 도구의 `scope`와 `action`으로 통합된 옛 이름(`search_guide`, `search_knowledge`, `list_common_components` 등)과 기능이 제거된 이름(`egov_ddl_assist`, `search_standard_terms`)은 등록되어 있지 않으며, 그 이름으로 호출하면 `isError` 결과로 `MCP error -32602: Tool <이름> not found`가 돌아옵니다.

### 4) Smoke Test 프롬프트

LLM 채팅창에 아래 프롬프트를 입력해 LLM이 본 MCP 도구를 자동으로 선택하는지 확인합니다.

```text
표준프레임워크에서 "트랜잭션 설정"에 대해 공식 가이드와 개발자 지식을 함께 찾아줘.
```

**기대 호출**

```json
{ "query": "트랜잭션 설정" }
```

**기대 결과**

- `scope`를 생략한 호출은 통합 검색으로 처리되고, 응답이 `# 통합 지식 검색 결과`로 시작함(`scope: "all"`을 명시해도 같은 결과임)
- 공식 가이드(`## eGovFrame 가이드 검색 결과 (5건)`), 개발자 지식(`## 개발자 지식 검색 결과`), 공통컴포넌트(`## 공통컴포넌트 목록 (8개 중 5개 표시)`), 호환 소프트웨어(`## 호환 소프트웨어 검색 결과`)의 네 섹션이 차례로 나옴
- 공통컴포넌트와 호환 소프트웨어는 키워드 검색이라서 이 `query`에 맞는 항목이 적음. 호환 소프트웨어 섹션은 `"total": 0`으로 나오며, 이것은 오류가 아님
- 어느 섹션에도 `검색 중 오류가 발생했습니다`가 없음

## 합격 기준

- [ ] `node -v`가 `v22.x`이고, 폐쇄망에서 `npm install`, 빌드, 인덱싱, 모델 다운로드 없이 반입한 배포본만으로 서버가 시작된다.
- [ ] MCP 클라이언트가 본 서버를 인식하고 `egov_search_knowledge` 1개를 노출한다(그 외 도구 없음).
- [ ] Smoke Test 프롬프트에서 LLM이 `egov_search_knowledge`를 호출하고, 공식 가이드와 개발자 지식의 결과가 각각 1건 이상 반환되며 응답에 `검색 중 오류가 발생했습니다`가 없다.

## 실패 시 대응

| 증상 | 1차 확인 |
|------|----------|
| `build/index.js` 없음 | tgz를 푼 경로와 클라이언트 설정의 `args` 경로가 같은지 확인. 설치 경로에서 `npm install`이나 `npm run build`를 실행했다면 tgz를 다시 풉니다 |
| 도구 목록이 비어 있음 | 클라이언트 설정의 `command`와 `args` 절대 경로, 서버 로그(stderr), 반입한 tgz의 플랫폼(os-cpu)이 서버와 맞는지 확인 |
| 응답에 `네이티브 모듈(better-sqlite3)을 불러오지 못했습니다` | 서버를 실행하는 `node`가 Node.js 22인지(`node -v`, 클라이언트 설정의 `command`), tgz의 플랫폼이 서버와 맞는지 확인 |
| 응답에 `임베딩 모델을 찾을 수 없습니다` | 설치 경로에 `models/Xenova/multilingual-e5-small/`이 있는지 확인 |
| 응답에 `임베딩 모델 파일을 읽지 못했습니다` | `models/` 아래의 파일이 반입하는 중에 손상되었거나 읽을 권한이 없는 경우입니다. tgz를 다시 풀고 MCP 서버를 재시작합니다 |
| 응답에 `지식베이스 DB(knowledge-base/egovframe.db)를 찾을 수 없습니다`, `공식 가이드 인덱스(knowledge-base/egovframe_guide.lance)를 찾을 수 없습니다`, `개발자 지식 인덱스(knowledge-base/developer_knowledge.lance)를 찾을 수 없습니다` 가운데 하나 | 설치 경로의 `knowledge-base/`에 해당 항목이 있는지 확인 |
| 응답에 `공식 가이드 인덱스를 읽지 못했습니다` 또는 `개발자 지식 인덱스를 읽지 못했습니다` | MCP 서버를 재시작합니다. 계속되면 `knowledge-base/` 아래의 인덱스 파일이 빠졌거나 손상된 경우이므로 tgz를 다시 풉니다 |
| 응답에 `공통컴포넌트 소스가 설치되어 있지 않습니다` | 설치 경로에 `templates/common-components-src/`가 있는지 확인. 없으면 서브모듈(`templates/common-components-src`)을 받은 저장소에서 tgz를 다시 만듭니다 |
