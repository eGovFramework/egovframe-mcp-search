# 시나리오 03: eGovFrame 버전별 호환 소프트웨어 검색

## 목적

사업 도입 단계에서 자주 묻는 "표준프레임워크 X.Y 버전과 함께 사용할 수 있는 솔루션은 무엇인가?"라는 질문에 폐쇄망 OSS LLM + 본 MCP가 답할 수 있는지 확인합니다.

## 검증 도구

- `egov_search_knowledge` (`scope`: `compatibility`)

## 사전조건

- 시나리오 00 통과
- 설치 경로에 `knowledge-base/egovframe.db`(호환 소프트웨어 목록)가 있음
- 관련 개발자 지식을 함께 조회하는 3-2에는 `knowledge-base/developer_knowledge.lance/`와 `models/`(임베딩 모델)도 있어야 함

## 시나리오

### 3-1) 버전 + 분류 조합 검색과 구간 조회

```text
eGovFrame 4.3 버전에서 사용할 수 있는 CMS Solution을 찾아줘.
```

**기대 호출**

```json
{ "scope": "compatibility", "filters": { "frameworkVersion": "4.3", "category": "CMS Solution" } }
```

**기대 결과**

- 도구 응답은 `## 호환 소프트웨어 검색 결과` 아래의 JSON이고, LLM이 이를 표로 정리해 보여 줌
- JSON에 `"total": 29`, `"count": 20`, `"limit": 20`, `"offset": 0`과 실제로 적용한 필터(`filters`)가 들어 있음. `total`은 조건에 맞는 전체 건수이고 `count`는 이번에 돌려준 건수임
- `software`의 항목마다 `product_name`, `product_version`, `framework_version`, `category`, `compatibility_level`, `vendor`, `verified_date`, `description`, `url`이 있고, 확인일자(`verified_date`)가 최근인 순으로 나옴
- 남은 결과가 있으므로 끝에 ``> 전체 29건 중 1~20번째 결과를 표시했습니다. 다음 구간은 같은 호출에 `filters.offset: 20` 을 주어 조회합니다.``가 붙음

이어서 다음을 입력합니다.

```text
나머지 제품도 이어서 보여줘.
```

**기대 호출**

```json
{ "scope": "compatibility", "filters": { "frameworkVersion": "4.3", "category": "CMS Solution", "offset": 20 } }
```

**기대 결과**

- `"total": 29`, `"count": 9`, `"offset": 20`으로 나머지 9건이 나오고 안내가 붙지 않음
- `offset` 대신 `limit: 30`을 줘서 29건을 한 번에 받는 호출도 유효함. `limit`의 최댓값은 50이고, 더 큰 값은 50으로 줄여 적용한 뒤 `> 요청한 limit 100 은(는) compatibility 범위의 최댓값 50 으로 줄여 적용했습니다.`를 붙임

### 3-2) 벤더 기준 검색과 관련 개발자 지식

```text
표준프레임워크와 호환되는 티맥스 제품을 알려줘. 벤더와 호환 레벨, 제품명, 표준프레임워크 버전을 같이 보여주고, 관련된 개발자 지식이 있으면 함께 보여줘.
```

**기대 호출**

```json
{ "scope": "compatibility", "filters": { "vendor": "티맥스", "includeKnowledge": true } }
```

**기대 결과**

- `"total": 5`이고, 제품 버전(표준프레임워크 버전)은 JEUS 21(4.3), Tibero v7(4.0), JEUS 8.5(4.0), JEUS 8(3.6), Tibero(3.6)임
- `vendor`는 업체명의 부분 문자열이므로 `(주)티맥스소프트`, `㈜티맥스티베로`, `(주)티맥스데이터`가 모두 일치함
- `vendor`는 법인 표기(`㈜`, `(주)`, `주식회사`)와 공백의 차이를 가리지 않음. 동봉 데이터에는 아이액츠가 `(주)아이액츠`, `㈜아이액츠`, `주식회사 아이액츠`의 세 가지 표기로 들어 있는데, `filters.vendor`에 이 가운데 어느 표기를 주어도, 법인 표기 없이 `아이액츠`만 주어도 같은 6건이 나옴. 응답의 `filters.vendor`에는 받은 값이 그대로 실림
- `relatedKnowledge`에 제품명 `JEUS`와 `Tibero`를 언급하는 개발자 지식이 제품별로 5건씩 나오고, 지식마다 `id`, `title`, `excerpt`, `type`, `importance`, `tags`가 있음. `excerpt`는 본문에서 제품명이 나오는 부분을 중심으로 한 200자 이내의 발췌임
- `knowledgeLookup`은 이번 응답에 나온 제품 가운데 몇 개의 관련 지식을 조회했는지 알려 줌. 이 호출에서는 `{ "searchedProducts": 2, "pageProducts": 2 }`임
- `filters.vendor` 대신 `query: "티맥스"`로 호출해도 같은 5건이 같은 순서로 나옴. 이때는 JSON에 `"matchMode": "all-terms"`가 더 들어감

### 3-3) 호환 레벨 필터

```text
eGovFrame 4.3과 호환 레벨 2인 솔루션 중에서 Framework Solution 분류만 뽑아줘.
```

**기대 호출**

```json
{ "scope": "compatibility", "filters": { "frameworkVersion": "4.3", "category": "Framework Solution", "level": 2 } }
```

**기대 결과**

- `"total": 3`으로 JnFrame, Anyframe, noaats Beyond framework(확인범위:시스템관리)가 나오고, 세 제품의 `compatibility_level`이 모두 2임
- `level`은 호환 레벨이 그 값과 같은 행만 고르고, `minLevel`은 그 값 이상인 행을 고름. 호환 레벨은 1과 2뿐이라서 LLM이 `level: 2` 대신 `minLevel: 2`를 보내도 같은 3건이 나옴
- `level: 1`로 바꾸면 호환 레벨 1인 NBizFrame 1건만 나옴. `minLevel: 1`은 모든 행이 해당하므로 레벨 필터를 뺀 것과 같은 4건이 나옴

### 3-4) 키워드 검색과 검색어 안내

```text
JEUS는 표준프레임워크 어떤 버전과 호환돼?
```

**기대 호출**

```json
{ "scope": "compatibility", "query": "JEUS" }
```

**기대 결과**

- `"matchMode": "all-terms"`와 `"total": 3`이 나오고, 제품 버전(표준프레임워크 버전)은 JEUS 21(4.3), JEUS 8.5(4.0), JEUS 8(3.6)임. `all-terms`는 결과의 모든 행에 모든 검색어가 들어 있다는 뜻임
- LLM이 질문 문장을 그대로 `query`로 보내도(`"query": "JEUS는 표준프레임워크 어떤 버전과 호환돼?"`) 같은 3건이 나옴. 이때는 모든 검색어가 들어 있는 행이 없어서 일부 검색어가 들어 있는 행을 찾았다는 뜻으로 `"matchMode": "any-term"`이 나오고, 다음 필드가 함께 실림
  - `"usedTerms": ["JEUS", "버전"]`: 검색에 쓴 검색어. 조사가 붙은 `JEUS는`과 `버전과`는 조사를 뗀 꼴로 찾음
  - `"requiredMatches": 1`: 결과의 행마다 일치한 검색어의 최소 수. `버전`은 거의 모든 행에 들어 있는 흔한 낱말이어서, 이 낱말만 일치한 행은 결과에 싣지 않음
  - `"ignoredTerms": ["어떤", "호환돼"]`: 일치하는 행이 없어서 쓰지 않은 검색어
  - `"droppedTerms": ["표준프레임워크"]`: 프레임워크 자체를 가리키는 낱말이어서 검색에서 뺀 검색어
- 키워드 검색은 필터를 적용한 범위 안에서 찾음. `{ "scope": "compatibility", "query": "Tibero", "filters": { "frameworkVersion": "4.3" } }`은 `"total": 0`이고, `"ignoredTerms": ["Tibero"]`와 `"totalWithoutQuery": 42`가 함께 나옴. 표준프레임워크 4.3의 42건 가운데 Tibero가 들어 있는 행이 없다는 뜻이므로, LLM이 필터를 빼거나 바꿔서 다시 호출하는지 확인함

## 합격 기준

- [ ] 3-1, 3-2, 3-3, 3-4의 기대 호출에서 결과가 1건 이상 반환된다.
- [ ] 3-1에서 두 번의 호출로 29건이 빠짐없이 조회된다.
- [ ] 응답의 `software` 항목에 **표준프레임워크 버전, 제품명, 벤더, 호환 레벨**이 모두 들어 있다.
- [ ] 모든 호출이 외부 네트워크 없이 완료된다.

## 점검 포인트

- `scope`를 생략해도 `frameworkVersion`, `vendor`, `minLevel`, `level` 같은 호환 소프트웨어 조회용 필터가 있으면 호환 소프트웨어 조회로 처리됩니다. 반대로 `scope`와 필터 없이 `query`만 보내면 통합 검색이 실행되어 호환 소프트웨어는 5건까지만 나옵니다. 예를 들어 `{ "query": "CMS" }`의 호환 소프트웨어 섹션은 299건 가운데 5건을 싣고, 끝에 ``> 전체 299건 중 1~5번째 결과를 표시했습니다. 다음 구간은 `scope: "compatibility"` 를 지정하고 `filters.offset: 5` 을 주어 조회합니다.``가 붙습니다.
- 응답의 `filters`에는 실제로 적용한 필터가 실립니다. LLM이 필터 키를 `filters` 객체 밖(인자의 최상위)에 두면 그 키는 오류 없이 버려집니다. 예를 들어 `{ "scope": "compatibility", "frameworkVersion": "4.3" }`은 `"filters": {}`와 `"total": 481`을 돌려줍니다. 이 값이 보이면 필터가 적용되지 않은 것입니다.
- `category`는 대소문자를 가리지 않지만 데이터에 있는 분류 이름이어야 합니다. 동봉 데이터의 분류는 `CMS Solution`, `CRM Solution`, `DBMS`, `Development Tool`, `ECM Solution`, `EDMS Solution`, `Framework Solution`, `GIS Solution`, `HR Solution`, `Mobile Solution`, `PMS Solution`, `Portal Solution`, `Report Solution`, `Security Solution`, `UX Solution`, `WAS`, `기타`입니다.
- 데이터에 없는 버전이나 분류로 조회하면 `"total": 0`과 함께 `available`에 쓸 수 있는 값(`frameworkVersions`, `categories`)이 나옵니다. 예를 들어 `filters.category: "RDBMS"`는 0건이고 `available.categories`에 `DBMS`가 들어 있습니다. LLM이 이 값을 보고 필터를 고쳐 다시 호출하는지 봅니다.
- `frameworkVersion`은 `"4.3"`, `"3.10"`처럼 메이저.마이너 형식의 문자열입니다. `"v4.3"`과 `"4.3.0"`은 `4.3`으로 맞춰 처리되지만, 숫자 `4.3`은 입력 검증 오류(`MCP error -32602: Input validation error ...`)가 됩니다. 동봉 데이터의 버전은 2.7, 3.0, 3.1, 3.5, 3.6, 3.7, 3.8, 3.9, 3.10, 4.0, 4.1, 4.2, 4.3입니다.
- `minLevel`과 `level`은 정수 1 또는 2입니다. 문자열 `"2"`나 3 이상의 값은 입력 검증 오류가 됩니다.
- 호환 소프트웨어의 `query`는 의미 검색이 아니라 키워드 검색에 쓰입니다. 검색어가 제품명, 제품 버전 표기, 업체명, 분류, 설명 가운데 하나에 부분 문자열로 들어 있으면 일치합니다. `Tibero`처럼 제품명이나 업체명에 들어 있는 낱말을 몇 개만 적을 때 잘 맞습니다. `한국 토종 RDBMS` 같은 문장에 가까운 `query`는 `"matchMode": "any-term"`, `"usedTerms": ["한국"]`, `"ignoredTerms": ["토종", "RDBMS"]`와 함께 업체명에 `한국`이 들어 있는 제품 4건을 돌려주며, 질문과 관련이 적습니다. 조건을 필터로 표현할 수 있을 때는 필터를 쓰도록 유도합니다.
- 표준프레임워크 버전은 `query`보다 `filters.frameworkVersion`으로 고르는 편이 정확합니다. `query: "3.1"`은 표준프레임워크 버전이 3.1인 행뿐 아니라 제품 버전 표기나 설명에 `3.1`이 들어 있는 행(`3.10` 포함)까지 86건을 돌려주지만, `filters.frameworkVersion: "3.1"`은 26건을 돌려줍니다. 확인일자는 `query: "2025-08"`처럼 연도나 연월을 적으면 그 값으로 시작하는 행과 일치합니다(4건).
- `includeKnowledge`는 결과의 앞에서부터 제품명 5개까지만 관련 지식을 찾고, 제목이나 본문에 제품명이 들어 있는 지식만 싣습니다. 그런 지식이 없으면 `relatedKnowledge`가 빈 배열입니다(예: 3-1의 호출에 `includeKnowledge: true`를 더한 경우. 이때 `knowledgeLookup`은 `{ "searchedProducts": 5, "pageProducts": 20 }`입니다). 임베딩 모델이 없어서 관련 지식을 조회하지 못한 경우에도 `software`는 그대로 나오고, 원인을 적은 `knowledgeWarning`이 함께 나옵니다.
- 호환 소프트웨어 조회가 쓰지 않는 필터는 무시되고 응답 끝에 그 키가 안내됩니다. 예를 들어 `filters.dbType`을 함께 보내면 끝에 `> 이 조회에 적용되지 않아 무시한 필터: dbType. (dbType 은(는) action "ddl" 또는 "dml" 에서 씁니다.)`가 붙습니다.
- 동봉 데이터에는 원본 값이 잘못 들어간 행이 있습니다. 확인일자에 날짜가 아닌 값이 든 행이 3건 있고, 이런 행은 목록의 맨 뒤에 나옵니다(3-1의 SmartManager). 3-2의 Tibero(표준프레임워크 3.6) 행은 `description`에 깨진 글자가 들어 있습니다. 분류 `DBMS`의 26건에는 `Any CMS`, `NWR CMS`처럼 DBMS가 아닌 제품이 섞여 있습니다. 모두 데이터의 문제이며 MCP 연동의 오류가 아닙니다.
