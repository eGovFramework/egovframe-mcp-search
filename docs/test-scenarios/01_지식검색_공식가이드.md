# 시나리오 01: 공식 가이드 검색과 통합 검색

## 목적

OSS LLM이 본 MCP의 `egov_search_knowledge` 도구를 이용해 **표준프레임워크 공식 가이드**를 폐쇄망에서 검색할 수 있는지 확인합니다. 출처를 정하지 않은 질문이 통합 검색으로 처리되는지, 통합 검색에서 찾은 개발자 지식의 전체 본문을 이어서 조회할 수 있는지, 공식 가이드의 긴 절을 조각 단위로 이어 읽을 수 있는지도 함께 확인합니다.

## 검증 도구

- `egov_search_knowledge` (`scope`: `guide`, `knowledge`, 그리고 `scope`를 생략한 통합 검색)

## 사전조건

- 시나리오 00 통과
- 설치 경로에 `knowledge-base/egovframe_guide.lance/`(공식 가이드 인덱스), `knowledge-base/developer_knowledge.lance/`(개발자 지식 인덱스), `models/`(임베딩 모델)가 있음

## 시나리오

### 1-1) 통합 검색

LLM 채팅창에 다음을 입력합니다.

```text
표준프레임워크에서 MyBatis 설정 방법을 공식 가이드와 개발자 지식에서 함께 찾아 비교해서 알려줘.
```

**기대 호출**

```json
{ "query": "MyBatis 설정 방법" }
```

**기대 결과**

- `scope`를 생략하거나 `"auto"` 또는 `"all"`로 지정한 호출은 모두 같은 통합 검색 결과를 돌려줌
- 응답이 `# 통합 지식 검색 결과`로 시작하고 공식 가이드, 개발자 지식, 공통컴포넌트, 호환 소프트웨어의 네 섹션이 차례로 나옴(출처마다 기본 5건)
- 공식 가이드 섹션(`## eGovFrame 가이드 검색 결과 (5건)`)의 결과마다 문서, 분류, 소스, URL, 유사도가 나오고, 분류는 대부분 `egovframe-runtime > persistence-layer`임
- 공식 가이드의 긴 절은 색인할 때 여러 조각으로 나뉘어 있음. 그런 절의 결과는 제목이 `(8/8)`처럼 조각 번호로 끝나고, `- **조각**:` 줄에 그 조각과 이웃 조각의 `chunkId`가 나옴(이 `query`에서는 `MyBatis Configuration XML File: Configuration XML > Sample Configuration` 절의 조각). 조각을 이어 읽는 방법은 1-5에서 확인함
- 개발자 지식 섹션(`## 개발자 지식 검색 결과`)은 JSON이며 결과마다 `id`, `title`, `content`, `tags`, `similarity`가 있음. `content`는 600자 이내의 발췌이고, 섹션 끝에 전체 본문을 보려면 `scope: "knowledge"`로 검색하라는 안내가 붙음
- 공통컴포넌트와 호환 소프트웨어 섹션은 키워드 검색이라서 문장에 가까운 `query`에는 잘 맞지 않음. 이 `query`에서는 공통컴포넌트 섹션(`## 공통컴포넌트 목록 (9개 중 5개 표시)`)에 `설정`이나 `방법`이 들어 있는 컴포넌트가 나오고, `> 모든 검색어가 들어 있는 항목이 없어, 검색어 2개 가운데 1개 이상이 들어 있는 항목을 표시합니다 (검색어: 설정, 방법).`과 `> 일치하는 항목이 없어 검색에 쓰지 않은 낱말: MyBatis.`가 붙음
- 호환 소프트웨어 섹션은 `"total": 0`임. 세 검색어가 모두 `ignoredTerms`에 들어 있고, `"totalWithoutQuery": 481`은 `query`를 빼면 481건이 있다는 뜻임

### 1-2) 공식 가이드만 한정 검색

```text
표준프레임워크 공식 가이드 기준으로만 트랜잭션 설정 방법을 찾아줘. 개발자 지식이나 공통컴포넌트 검색 결과는 제외해줘.
```

**기대 호출**

```json
{ "query": "트랜잭션 설정 방법", "scope": "guide" }
```

**기대 결과**

- 응답에 `## eGovFrame 가이드 검색 결과 (5건)`만 나오고 다른 출처의 섹션이 섞이지 않음
- 명시한 `scope`는 항상 그대로 적용됨. `strictScope`는 효과가 없는 파라미터라서 LLM이 `strictScope: true`를 함께 보내도 결과는 같음

### 1-3) 분류 필터를 적용한 검색

```text
표준프레임워크 공식 가이드 중 persistence-layer 영역에서 트랜잭션을 어떻게 설명하는지 보여줘.
```

**기대 호출**

```json
{ "query": "트랜잭션", "scope": "guide", "filters": { "category": "persistence-layer" } }
```

**기대 결과**

- 결과 5건의 분류가 모두 `egovframe-runtime > persistence-layer`임
- `filters.layer: "egovframe-runtime"`을 함께 줘도 결과는 같음. `scope`를 생략해도 `category` 값이 공식 가이드의 분류이므로 가이드 검색으로 처리됨
- `layer`는 최상위 영역(`egovframe-runtime`, `egovframe-development`, `common-component`)이고 `category`는 그 아래의 분류임. `filters.layer: "egovframe-runtime"`만 주면 `foundation-layer-core` 같은 다른 분류의 문서가 섞임
- 값을 잘못 넣은 호출(예: `filters.layer: "persistence-layer"`)은 `isError` 응답으로 `알 수 없는 layer 값입니다: "persistence-layer". 사용할 수 있는 값: egovframe-runtime, egovframe-development, common-component, gettingstarted.md`를 돌려줌. LLM이 이 목록을 보고 값을 고쳐 다시 호출하는지 확인함

### 1-4) 개발자 지식의 전체 본문 조회

1-1에 이어서 다음을 입력합니다.

```text
방금 찾은 개발자 지식의 전체 본문을 보여줘.
```

**기대 호출**

```json
{ "query": "MyBatis 설정 방법", "scope": "knowledge" }
```

**기대 결과**

- 응답에 `## 개발자 지식 검색 결과` 아래의 JSON만 나오고 `resultCount`가 5임
- 1-1과 같은 글이 같은 순서로 나오며, `content`에 질문과 답변의 전체 본문이 들어 있음
- `tags`로 출처를 구분할 수 있음: `qa`는 묻고답하기, `faq`는 FAQ, `guide`와 `pdf`는 적용가이드
- `filters.tags`로 출처를 좁힐 수 있음. 예를 들어 `filters.tags: ["pdf"]`를 더하면 적용가이드에서 나온 결과만 나옴(태그는 대소문자를 가리지 않음). 데이터에 없는 태그(예: `"mybatis"`)를 주면 0건이 되고 끝에 `> filters.tags 의 "mybatis" 은(는) 데이터에 없는 태그입니다. 데이터에 있는 태그: egovframe, developer_knowledge, qa, faq, guide, pdf (대소문자는 가리지 않습니다).`가 붙음

### 1-5) 조각으로 나뉜 절과 잘린 본문 이어 읽기

검색 결과가 조각으로 나뉜 절의 일부이거나 본문이 잘려 있을 때, 응답에 적힌 `chunkId`로 나머지를 읽을 수 있는지 확인합니다.

```text
표준프레임워크 공식 가이드에서 Maven의 특징을 찾아줘.
```

**기대 호출**

```json
{ "query": "Maven의 특징", "scope": "guide" }
```

**기대 결과**

- 1번 결과의 제목이 `개인빌드(Maven): 설명 > Maven 특징 (2/2)`이고, 머리말에 `- **조각**: 2/2 (이 조각의 chunkId: "…", 이전 조각: "…")` 줄이 있음. 첫 조각에는 다음 조각의 `chunkId`만, 마지막 조각에는 이전 조각의 `chunkId`만, 가운데 조각에는 둘 다 적힘
- 결과 하나에 싣는 본문은 1,500자까지임. 1번 결과는 본문이 더 길어서 끝에 ``> 전체 2,416자 중 1~1,500자를 표시했습니다. 나머지는 `scope: "guide"`, `filters.chunkId: "…"`, `filters.offset: 1500` 으로 이어서 읽을 수 있습니다.``가 붙음
- 같은 절의 조각이 여러 개 검색되면 유사도가 가장 높은 조각 하나만 결과로 실림. 1번 결과 아래의 `> 같은 절의 다른 조각도 검색되었습니다: 1/2 (chunkId "…").`가 함께 검색된 나머지 조각을 알려 줌

이어서 다음을 입력합니다.

```text
1번 결과의 잘린 뒷부분을 이어서 보여주고, 같은 절의 앞 조각도 보여줘.
```

**기대 호출**

```json
{ "scope": "guide", "filters": { "chunkId": "<1번 결과의 조각 줄에 적힌 이 조각의 chunkId>", "offset": 1500 } }
```

```json
{ "scope": "guide", "filters": { "chunkId": "<1번 결과의 조각 줄에 적힌 이전 조각의 chunkId>" } }
```

**기대 결과**

- `filters.chunkId`를 준 호출은 검색하지 않고 그 청크를 읽으므로 `query`가 필요 없음. 응답은 `## <청크 제목>` 아래에 문서, 분류, 소스, URL과 본문을 돌려줌
- 첫 번째 호출은 `## 개인빌드(Maven): 설명 > Maven 특징 (2/2)`의 나머지 본문을 돌려주고, 끝에 `> 전체 2,416자 중 1,501~2,416자를 표시했습니다 (청크의 끝).`과 ``> 이 절은 2조각으로 나뉘어 있고, 이 청크는 2번째 조각입니다. 이전 조각의 chunkId 는 "…" 입니다 (`filters.chunkId` 에 넣어 읽습니다).``가 붙음
- 두 번째 호출은 `## 개인빌드(Maven): 설명 > Maven 특징 (1/2)`의 본문 전체를 돌려주고, 끝에 `> 전체 2,409자 중 1~2,409자를 표시했습니다 (청크의 끝).`과 다음 조각의 `chunkId`를 알리는 안내가 붙음
- LLM이 `query`나 `limit`을 함께 보내도 청크는 그대로 읽히고, 끝에 `> 이 조회에 쓰이지 않아 무시한 파라미터: query, limit.`처럼 쓰이지 않은 파라미터의 이름이 안내됨
- 없는 `chunkId`를 주면 `isError` 응답으로 `filters.chunkId 에 해당하는 가이드 청크를 찾을 수 없습니다: <받은 값>. 청크 ID 는 지식베이스를 갱신하거나 다시 구축하면 바뀝니다. scope guide 로 다시 검색해서 새 ID 를 확인하세요.`가 돌아옴

### 1-6) 통합 검색의 출처별 상한

```text
MyBatis 설정 방법을 출처마다 30건씩 찾아줘.
```

**기대 호출**

```json
{ "query": "MyBatis 설정 방법", "limit": 30 }
```

**기대 결과**

- 통합 검색은 출처마다 최대 10건을 싣기 때문에 공식 가이드 섹션이 `## eGovFrame 가이드 검색 결과 (10건)`이고 개발자 지식 섹션의 `resultCount`가 10임. 공통컴포넌트 섹션에는 일치하는 9개가 모두 나오고(`## 공통컴포넌트 목록 (9개)`), 호환 소프트웨어 섹션의 `limit`은 10임
- 응답의 맨 끝에 ``> 통합 검색은 출처마다 최대 10건을 싣습니다. 요청한 limit 30 은(는) 10 으로 줄여 적용했습니다. 한 출처의 결과를 더 보려면 `scope` 로 그 출처를 지정해 조회하세요.``가 한 번 붙음
- LLM이 이 안내를 보고 출처를 지정해 다시 호출하는지 확인함. 예를 들어 `{ "query": "MyBatis 설정 방법", "scope": "guide", "limit": 30 }`은 공식 가이드의 최댓값인 20건을 돌려주고, 끝에 `> 요청한 limit 30 은(는) guide 범위의 최댓값 20 으로 줄여 적용했습니다.`가 붙음

## 합격 기준

- [ ] 1-1에서 통합 검색 응답의 공식 가이드 섹션과 개발자 지식 섹션에 결과가 각각 1건 이상 있다.
- [ ] 1-2에서 공식 가이드 검색 결과만 반환된다.
- [ ] 1-3에서 반환된 결과의 분류가 모두 `egovframe-runtime > persistence-layer`이다.
- [ ] 1-4에서 개발자 지식의 전체 본문이 반환된다.
- [ ] 1-5에서 LLM이 응답에 적힌 `chunkId`로 잘린 본문의 나머지와 앞 조각을 읽는다.
- [ ] 1-6에서 출처마다 10건까지만 반환되고, 줄여 적용했다는 안내가 응답에 있다.
- [ ] 모든 호출이 외부 네트워크 없이 완료된다.

## 점검 포인트

- LLM이 "`scope`를 직접 정하라"는 안내 없이도 적절히 `scope`를 추론하는지 확인합니다. 만약 LLM이 매번 사용자에게 `scope`를 되묻는다면, 시스템 프롬프트나 도구 description이 잘 전달되지 않은 것입니다.
- 결과 응답이 너무 길어지면 `limit`을 2~3으로 줄여 다시 시도합니다. 공식 가이드와 개발자 지식의 기본값은 5건(최대 20건)이고, 통합 검색은 출처마다 기본 5건(최대 10건)입니다. 통합 검색에 `limit`을 주면 출처마다 그 건수가 적용됩니다.
- 통합 검색의 한 섹션에만 `검색 중 오류가 발생했습니다`가 나오면 그 출처만 실패한 것이고 나머지 섹션은 정상입니다. 네 출처가 모두 실패한 응답은 `isError`로 돌아옵니다. 오류 문구별 확인 사항은 시나리오 00의 "실패 시 대응"에 있습니다.
- 공식 가이드 결과의 본문은 원문 마크다운의 제목 줄을 굵은 글씨로, 구분선을 `* * *`로 바꿔 실은 것입니다. 결과의 제목(`### 1. ...`)과 결과 사이의 구분선(`---`)을 본문과 구별하기 위한 처리이며, 원문이 깨진 것이 아닙니다.
